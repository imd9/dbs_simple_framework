## One-line meeting purpose
Align the iDEE-for-Databricks framework/application folder structure, clarify what belongs in framework vs application code, reset focus away from asset bundles/CICD, and define the next demo around a minimal working YAML config parser/validator flow.

## Core guidance / decisions
1. Work must proceed one complete unit at a time. Avoid building many disconnected pieces at once.
2. Current priority is not Databricks asset bundles, CICD, or repo deployment. Those come later once repos/AD groups are ready.
3. Immediate priority is a minimal working configuration flow:
   - Create/populate a simple sample YAML config for one pipeline.
   - Validate it against the expected schema.
   - Parse it through framework code.
   - Produce clear output showing what metadata/table actions would happen.
   - Add PyTest/unit tests for framework code.
4. Keep framework and application concerns separate.
5. The framework is responsible for reusable logic: templates, schema validation, config parsing, orchestration/main scripts, metadata DDL/setup, and unit tests.
6. The application folder is for a downstream application/user example: filled config files, sample application DDL, sample data, and simple test pipeline artifacts.
7. A YAML template belongs in the framework, likely under a templates folder.
8. A copied and filled YAML config is no longer called a template and belongs in the application folder.
9. Config parsing belongs in the framework, not in the application folder.
10. Application DDL belongs in the application folder because it is app/Jira-story/requirement specific.
11. Metadata DDL belongs with framework setup because it is framework-owned and run as part of environment/setup.
12. Unit tests should primarily be for framework code. Application sample data/pipelines may have simple validation, but the priority is framework PyTest coverage.
13. Use consistent folder naming, file naming, casing, and terminology from the beginning.
14. Do not use vague/random names such as lightweight, root, rootmaster, dry run test, or mixed naming styles in production-oriented folders.
15. Maintain a clean shared workspace. Put brainstorming or experimental ideas elsewhere rather than mixing them into the working folder.
16. Data quality, asset bundles, migrations, incremental load logic, append logic, and complex ingestion patterns are later stages after the first minimal skeleton works.
17. The first target demo should be intentionally simple: a tiny pipeline, one source, one target, about five columns, full refresh/truncate-and-load style.
18. Once the simple full-refresh path works, then add append, then incremental/delta handling, then more complex features.
19. The demo to Rashid should not happen before a review/demo with Ojoma after she returns, except for an informal status update in one-on-one context.
20. For status updates to Rashid, frame progress as step-by-step, quality-first, with clear separation between framework engineer and downstream application engineer perspectives.

## Minimal demo path
1. Start with a filled sample YAML config for one simple pipeline.
2. Run framework validator against the config.
3. Validator confirms config matches expected schema/version.
4. Run framework parser against the validated config.
5. Parser produces metadata output or insert/DML-like output for target metadata tables.
6. Show logs/status messages such as:
   - loading started
   - config version detected
   - config schema validation passed
   - parser completed
   - metadata table action list generated
   - load complete / output ready
7. Optional next pass: actually load metadata tables after DDL exists and is tested.
8. Demo from a Databricks cell/notebook by calling the framework command against the YAML file.

## Technical definitions clarified
- Template YAML: Blank/reusable framework-owned file that users copy.
- Filled YAML/config: Application-owned copy populated for a specific sample/application pipeline.
- Config validator: Framework process that checks whether the filled config conforms to the expected schema.
- Config parser: Framework process that reads valid config and translates it into metadata actions/SQL/inserts/load instructions.
- Unit tests/PyTest: Automated tests for Python framework classes/functions/modules to prevent regressions.
- Full refresh / truncate-and-load: First simple ingestion pattern; delete/drop existing target data and reload all source data.
- Append: Add all source rows onto target; not the same as incremental.
- Incremental/delta: Load only what exists in source and not already in target, based on delta logic.
- Hello-world pipeline: Ultra-simple sample pipeline that proves the framework works without external complexity.
